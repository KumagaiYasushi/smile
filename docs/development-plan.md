## 今回の実装範囲と互換性

- `event_type` は `BASIC_COURSE` / `LECTURE` / `SEMINAR` の3値。
- SQLiteの既存 `seminars` テーブルへ列を追加。既存レコードの種別は `SEMINAR`。
  元のID・日付・参加者関連・チェック項目・更新日時を変更しない。
- 作成APIで種別を省略した既存クライアントは `SEMINAR`、更新で省略した場合は現在値を維持。
  明示的な不正値やnullはHTTP 400。DBにもCHECK / NOT NULL制約を置く。
- `/api/seminars` と既存画面URLは維持。新規作成時は登録済みテンプレートから生成できる。種別の編集では既存タスクを変更しない。
- 作成・編集フォーム、一覧の種別表示と絞り込み、詳細表示を追加。
- 標準タスクの内容と逆算日数は利用者が登録する。架空テンプレートで種別別自動生成を検証済み。
  実運用の業務受入や、AT01〜AT20すべての合格を示すものではない。

## 依存関係に沿った次の開発

1. 基盤設計：本番ホスティング・DB・認証候補、費用条件、MFA・バックアップ・2名承認の可否を比較。
   U01/U07/U08/U10/U27の判断前に契約やアカウント連携を行わない。
2. 認証・権限・管理者MFA、テスト／本番分離、監査ログ、基本CI。ユーザーIDを後続の担当者・変更者に利用。
3. 開催回とタスク：手動管理、テンプレート、逆算生成、日程変更時の差分と個別判断付き再計算は実装済み。
   タスクダッシュボードも実装済み。今後は実運用テンプレートの確認、開催回、イベント状態の管理。日程変更例外 U11 の正式運用は未確定。
4. 参加者：横断マスター・申込・スナップショット・実出欠の分離、名寄せ、入金履歴、定員・待機者。
5. 外部データ・対外連絡：モックで過去取込／冪等同期／フォームプレビュー／Gmail／資料／告知を検証。
6. 通知、返金保護、開催後業務、改善要望。全領域を初期開発範囲に残す。
7. 障害・復元・権限・回帰試験、管理者2名の承認後に1イベントで試験運用。

## データ移行・API・権限の後続設計

- 現在の `participants` はイベント申込と人物情報を兼ねる。将来の移行では
  `participants`（人物）／`registrations`（イベント申込と受付時情報）／`attendance`（実出欠）へ分離する。
  移行中は旧IDとの対応表を保持し、バックアップ・件数・参照整合性・復元を検証して切り替える。
- イベントとタスク、申込と会計、外部同期キーは仕様書13章のモデルを候補とする。
  本番DB・認証方式の決定後、マイグレーションとAPI認可を設計する。
- 運営メンバーはイベント・会計・返金口座詳細を仕様の範囲で扱える。
  優先度最終決定・本番管理は管理者2名の権限。未ログインは管理APIに到達させない。
- Google／LINE／Gmail／Dropboxは未接続。外部API送信・公開・招待・本番デプロイを実装テストから実行しない。

## 検証

- `npm test`：一時DBで新規保存・種別変更・既存DB移行・再起動・不正種別の拒否を検証。
  アプリの `data/` をテストに使わない。
- `npm run build`：ビルドとTypeScript検査。
- `npm run lint`：既存メール画面のHook依存配列警告は別件。
- 開発サーバーで3種別の作成・更新・不正入力拒否・種別省略の互換性を確認し、架空データは削除する。
  ビルド後に `npm run test:smoke` を実行。独立したサーバーと一時DBで認証後にイベント種別も検証する。
  画面のHTMLとAPIを検証する。`npm run test:browser` でChromiumの3画面幅と管理者MFAも確認済み。実機・他ブラウザーは未確認。詳細は [ui-validation.md](ui-validation.md) を参照。
- 仕様書AT01〜AT20は引き続き受入基準。今回の種別実装だけで全項目合格とは扱わない。
