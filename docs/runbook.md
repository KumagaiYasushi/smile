# 開発・検証手順

Macでご自身が操作する手順は [Macでの確認手順](verify-on-mac.md) を参照してください。

既存の隔離された`/workspace/smile`を使う。ユーザーが明示的に求めない限りGit worktreeを作らない。

## 準備

Node.js 24.19.0、npm 11.9.0で確認。プロキシ・CA検証・既存Git認証を維持する。

```bash
cd /workspace/smile
npm ci --no-audit --no-fund
npm test
npm run lint
SMILE_ENV=test npm run build
npm run test:http
```

`test:http`はポート3107でローカルサーバーを起動し、ランダムな`data/test/<実行ID>/`に架空管理者・セミナー・参加者を作成する。終了時に自分のサーバーを停止し、そのDBディレクトリだけ削除する。固定の既存テストDBや旧DBは使用しない。ビルド中と開発サーバー実行中の`.next`への同時書込みは避ける。

## 架空管理者の作成と画面確認

ローカルターミナルで、管理者ごとに次を実行する。パスワードは12〜256文字。実在のアドレス・本人情報は入力しない。端末の履歴にパスワードを書かない。

```bash
cd /workspace/smile
export SMILE_ENV=development
export SMILE_DEV_EMAIL=admin-a@example.invalid
export SMILE_DEV_NAME=架空管理者A
read -r -s -p '開発専用パスワード: ' SMILE_DEV_PASSWORD
export SMILE_DEV_PASSWORD
npm run dev:admin
unset SMILE_DEV_PASSWORD
npm run dev -- --hostname 127.0.0.1 --port 3000
```

管理者Bは別の`.invalid`アドレスで同じ手順を使う。最大2名で、既存ユーザーを上書きしない。管理者の実名やメールは本番採用後の設定事項U10。

ログイン画面でメールとパスワードを入力し、初回だけ表示されるキーを認証アプリへ登録する。6桁コードでログイン→ホーム→セミナー一覧→新規作成→ログアウトを確認する。次回は保存した認証アプリのコードを入力する。画面に表示されたキーや認証コードのスクリーンショットを共有しない。

ブラウザー操作を伴う上記手順は手動確認項目。自動HTTPテストはHTML応答・APIを検証するが、ブラウザーでの入力やスマホ表示の確認を代替しない。

## 自動ブラウザー操作試験

Playwrightを開発用依存関係に固定している。先に`SMILE_ENV=test npm run build`を実行し、利用環境にChromiumを準備する。今回のクラウド環境には`/usr/bin/chromium`があり、次で12項目の成功を確認した。

```bash
SMILE_CHROMIUM_PATH=/usr/bin/chromium npm run test:browser
```

Playwright管理のブラウザーを使う環境では`npx playwright install chromium`で準備し、`npm run test:browser`を実行する（利用OSの依存ライブラリーが必要）。この追加インストール方式やmacOSでの実行は今回試していない。

ポート3108を使用し、実行ごとに別の架空DBを作る。終了時にサーバーとDBを片付け、スクリーンショットと結果だけを`data/reports/browser-verification/<実行ID>/`に残す。PC・スマートフォン幅はChromium内で検証するが、Safariや実機の検証を代替しない。

## 第2段階の手動確認

1. ログイン後「標準タスク」を開く。対象・名称・開催初日からの日数・開催前／当日／開催後・重要指定を登録する。これは架空の検証項目とし、本番の標準手順を決定したことにしない。
2. 「イベント」→「イベント作成」。種別、責任者、名称、初回日時を登録し、必要なら開催回を追加する。日時は日本時間で入力する。定員や参加費は空欄なら未定として保存する。
3. 詳細で自動生成されたタスクの期限を確認。主担当・協力者・4状態・重要指定・期限を変更して保存し、操作履歴とホーム表示を確認する。管理者Bの架空アカウントを作成しておくと、主担当と協力者を分けて試せる。
4. 固有タスクを追加する。標準テンプレートを編集しても作成済みタスクが書き換わらないことを確認する。
5. 日程変更の差分確認で新しい初回日を入力する。期限案は表示されるが保存されない。完了済みや個別期限は判断待ちとして表示する。

テンプレートがない種別は作成できないため、先に登録する。編集の競合が表示されたら「最新情報を再読み込み」またはページの更新を行い、内容を確認して再入力する。旧セミナーと新イベントは別管理で、旧参加者を自動移行しない。

## 第3段階の手動確認

1. 新イベントの詳細から「申込情報を管理」を開き、架空の氏名・携帯・メール・勤務先を記録する。氏名／携帯が不明なら空欄にできるが、全て空欄の記録は拒否する。
2. 別イベントで同じ氏名と携帯を入力し、同じ参加者の履歴に2件の申込が表示されることを確認する。電話の区切りや氏名の空白は勝手に正規化しない。
3. 「参加者マスター」で検索する。検索語はURLへ表示しない。履歴から「現在の代表情報」を確認して編集し、以前の申込時情報と変更前の値が残ることを確認する。
4. 氏名のみ・携帯のみ一致の架空データでは新しい参加者になることを確認する。複数一致は候補を表示し、統合ボタンは提供しない。
5. 全ての申込は「受付確認待ち」「出欠未確認」。これを確定参加者数・受講回数として使用しない。入金・出席・繰り上げ・返金はこの段階の操作対象ではない。

手動登録はリクエストキーで再試行の重複を防ぐ。同じキーで内容を変えた場合は409となるため、登録済みの内容を確認する。実際のGoogle回答IDによる同期・過去シート取り込みはまだ行わない。

## 第4段階の手動確認

第4段階では各イベントの申込情報画面で、定員・確定数・残席・締切を確認できる。定員未設定なら値を入力して確認チェック後に保存する。各未確定申込の内容と照合結果を確認し、チェックを入れて「受付を確定」を押す。確定者と日時が残る。満席・締切後はボタンを利用できず、サーバーも拒否する。受付確定は入金・出欠の確認ではない。取消は未対応なので架空データだけで試す。

## 保存領域・停止と再開

- 開発DB：`data/development/seminars.db`。MFA暗号化鍵：同じ開発ディレクトリの`auth.key`（DBとは別ファイル）。ソース管理対象外。
- 従来の`data/seminars.db`は読み込み・移行しない。
- `SMILE_ENV`未指定／`production`はDBアダプターが拒否する。ローカルの`next start`でも`SMILE_ENV=development`等の明示指定が必要。
- ライブプロセスはタスク再起動後に残ると仮定せず、作業ディレクトリと環境変数を確認して起動し直す。
- 認証アプリ紛失時の安全な回復は本番方式とともに未実装。SQLでMFAを無効化して運用を続ける手順は採用しない。検証は独立した架空DBでやり直す。

## 本番運用の未実装項目

毎日のバックアップ・30日保持・復元試験、鍵の独立保管、障害監視、管理者2名承認とロールバックは今後の本番準備段階に含める。CIは検証のみで、デプロイや外部送信のジョブは設けていない。今回の合格を本番運用開始の合格と解釈しない。
