# 認証・権限・個人情報

これはローカル検証用の土台であり、本番対応済みの認証製品ではない。採用サービス選定前の暫定実装である。

## 第1段階の実装

- 架空の管理者をCLIで作成し、メール＋パスワードとTOTPを両方確認する。公開登録APIや既定の共通パスワードは作らない。
- パスワードはランダムsalt付きscrypt。セッションは256ビット乱数を発行し、DBにはSHA-256ハッシュのみ保存。MFA前のチャレンジをセッションとして扱わない。
- 初回のパスワード検証後だけ認証アプリ用キーを提示し、正しいTOTPを入力するまで登録／ログイン完了にしない。TOTPはSHA-1・6桁・30秒、前後1ステップを許容し、使用済みステップを再利用しない。
- MFA秘密はAES-256-GCMで保存。鍵はDBと別の`auth.key`（権限600）。本番用のKMS／秘密管理サービス、鍵ローテーション・回復・バックアップは未実装。
- CookieはHttpOnly、SameSite=Strict、HTTPS時Secure。有効期限のほか、アカウントのactive状態とMFA状態を要求ごとに照合する。ログアウトでDBセッションを削除する。
- 変更APIは同一Originのみ許可。Cookieに加えてサーバー側でOriginを比較し、画面を非表示にするだけのアクセス制限にしない。
- 画面とAPIにno-store、no-referrer、nosniff、フレーム拒否を設定。認証情報をURLやアプリ監査へ含めない。
- ログインの失敗を制限し、期限切れ・使用済み・失敗回数超過のMFAチャレンジは拒否する。

## 本番前に残る作業

管理された認証サービス／ライブラリーの選定、実ユーザー本人確認・招待・パスワード回復、MFA回復と再登録、共有IPを考慮したレート制限、鍵保管とローテーション、HTTPSと信頼プロキシ、セキュリティレビュー。イベント・会計・口座詳細閲覧の監査、データ保持と削除、バックアップ30日保持／復元時再削除、2名承認の技術的強制は別段階で検証する。

認証監査には内部ユーザーID・種別・時刻だけを記録する。第2段階の業務監査はイベント／タスクID、担当ID、状態、重要指定、期限、操作時刻と前後差分を許可リストで記録する。名称・説明・メール、入力パスワード、TOTP、MFA秘密、トークン、口座番号は記録しない。画面での履歴表示は現在のイベントと照合し、担当やタスク名を表示する。

## 第3段階の参加者情報

参加者マスター・申込時情報・連絡先の変更履歴は、認証後の画面／APIだけが取得する。申込時情報と履歴には前後の連絡先を保持するが、これらを一般監査ログと混同しない。participant_audit_logsには内部ID、操作、変更項目名、時刻だけを記録し、値そのものをコピーしない。

検索語はPOST本文で送信し、URLやブラウザー履歴・アクセスログのクエリへ書き込まない。エラー応答は入力の値を反射しない。ブラウザー自動入力を使って実際の連絡先を持ち込まないよう、検証フォームの自動入力を無効にし、架空データの確認を求める。

申込時情報はDBのUPDATE禁止トリガーで保持し、代表情報編集とは切り離す。削除や訂正要求への正式な運用はU28の判断待ち。ローカルの参加者データ・連絡先履歴は現段階ではSQLite内の平文であり、実データ使用を許可する設計ではない。本番採用時にDB・バックアップの暗号化、権限、保持・削除、監査と復元を検証する。
