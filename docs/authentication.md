# 認証・権限基盤（ローカル開発版）

## 今回できること

- メール・パスワードで運営メンバーがログイン。公開の新規登録APIは設けない。
- 管理者は初回に認証アプリを登録し、6桁のTOTPを確認して初めて管理画面・業務APIへアクセスできる。
  以降のログインでも確認コードを要求する。管理者アカウントは有効な2名まで。
- 管理者だけがアカウント一覧を閲覧し、アカウント作成APIを利用できる。
  運営メンバーは既存のイベント・参加者・手動入金機能を引き続き利用できる。
- 未ログインのページアクセスは `/login` へ誘導。全業務APIは各ハンドラーで認証し、未認証は401、権限不足は403。
  レイアウトの表示制御だけに認可を依存しない。
- ログアウトでセッションをサーバー側から削除。期限切れ・無効化アカウント・管理者への変更前のメンバーセッションも拒否。
- 認証・ユーザー作成の監査記録を保存。パスワード、確認コード、MFAキー、セッション原文を監査へ含めない。

## 開発環境での初回設定

作業ディレクトリは `/workspace/smile`。既存チェックアウトを使用する。
以下は開発用のローカル操作であり、本番サービスの採用・外部アカウントの契約ではない。

1. `npm run auth:key` で開発用のMFA暗号化キーを生成する。
   既存の `AUTH_MFA_KEY` は保持する。新規キーはGitで無視される `.env.local` に保存され、値は表示しない。
2. `npm run user:create -- <管理者のメールアドレス> admin` を実行し、非表示の入力欄へパスワードを入力する。
   パスワードは12〜128文字。コマンド引数・チャット・ソースコードへ書かない。
3. 必要なら2人目の管理者を同じ手順で作成する。一般メンバーは末尾を `member` にする。
4. `npm run dev -- --hostname 127.0.0.1 --port 3000` で起動する。
   キー設定前からサーバーを起動していた場合は、自分で起動したサーバーを再起動する。
5. ログイン画面でメール・パスワードを入力し、管理者は認証アプリへセットアップキーを手動登録する。
   アプリ側はTOTP、SHA-1、6桁、30秒。表示キーは第三者に共有しない。
6. コード確認後にイベント一覧へ進める。管理者にはアカウント一覧へのリンクも表示される。

本タスクでは実ユーザーのアカウントや固定の初期パスワードは作成しない。
アカウント発行APIは `POST /api/admin/users`（メール・パスワード・role、管理者ログインと同一Originが必要）。
現在の画面はアカウント一覧のみで、発行は上記ローカルCLIまたは管理者APIで行う。

## 保存・秘密設定

- `SMILE_DATA_DIR`：DB格納ディレクトリ。未設定時は作業ディレクトリの `data/`。
  テストでは新規一時ディレクトリを指定し、既存DBに接続しない。
- `AUTH_MFA_KEY`：64桁の16進文字列（32バイト）。MFAのAES-256-GCM暗号化キー。
  本番ではDB・バックアップとは別の秘密保管領域で管理する。DB・配布物へ含めない。
  未設定時は管理者作成／管理者ログインを503で拒否する。
- `APP_ORIGIN`：公開するアプリのOrigin。リバースプロキシや本番では実URLを明示する。
  未設定のローカル開発では受信リクエストURLのOriginと比較する。
- ビルドのファイル追跡から `data/` と `.env*` を除外する。
  永続DBとキーは実行環境で別途用意する。キーを削除・再生成すると登録済みMFAを復号できなくなるため保持する。

## 実装上の保護

- パスワード：ユーザー別16バイトsalt、scrypt N=32768/r=8/p=1、32バイト導出値。
- セッション：256ビット乱数、DBにはSHA-256ダイジェストのみ。通常8時間、MFA前の仮認証5分。
- Cookie：HttpOnly・SameSite=Strict・Path=/。productionではSecureを付与しHTTPSで利用する。
  `next start` はproductionになるため、通常のローカルブラウザー確認は `next dev` を使う。
- 全書き込みAPIでOrigin照合。認証レスポンス・業務APIはno-store。
- TOTPは前後1ステップを許容。確認済みカウンターを更新し、同じコードの再利用を拒否。
  MFA完了時は同一ユーザーの仮認証を失効する。
- DBで試行制限を共有：ログインはメールごと8回/15分、全体100回/分、MFAは仮認証ごと5回/5分。
  期間・セッション期限・パスワード長は今回のローカル実装値であり、追加の業務決定として確定しない。
- 参加者詳細APIはURLのイベントIDと参加者の所属も照合し、別イベントのURLでは404にする。

## 検証方法

```sh
npm test
npm run build
npm run test:smoke
npm run lint
```

単体テストはメモリDBと一時DBを使用。TOTPはRFC 6238の既知ベクトルとも照合。
結合テストは3100番に独立したローカルサーバーを起動し、ランダム生成の架空資格情報と一時DBだけを使用する。
認証後にイベント種別テストも実行し、終了時にサーバーと一時データを片付ける。先にビルドが必要。
サンドボックスで子プロセスやポートがEPERMになる場合は、該当コマンドに対応した実行許可を使用する。

## 本番化前に残る作業

仕様書U01に従い、正式な認証・DB・ホスティング構成、費用、MFAと復旧機能を比較して管理者2名で判断する。
このローカル実装だけで本番運用可能とは扱わない。

- 一般メンバーの任意MFA登録画面、パスワード変更・再設定、招待・メール所有確認。
- 管理者の認証アプリ紛失時の本人確認・復旧手順、キーの保管・ローテーション、セッション一括失効。
- ユーザー無効化・権限変更の管理画面（DB上の無効化と権限変更はセッション検証に反映済み）。
- 実利用者2名の本人設定、別テストWEB環境、本番と分離したDB・キー、HTTPS・運用Origin設定。
- 業務データ変更の監査、バックアップ・復元試験、基本CI、iOS・Android実機とSafari等での操作試験。Chromiumのログイン・管理者MFA・アクセス制御は[画面操作テスト](ui-validation.md)で確認済み。
- 本番向けの認証方式・負荷・試行制限・復旧・権限のレビューと、仕様書AT01〜AT20の受入試験。
