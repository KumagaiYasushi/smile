# 開催日・期限変更

## 操作手順

1. イベント詳細の「開催日・期限変更」を開く。
2. 新しい開催日を入力する。複数日程の場合は、逆算に使う基準日を選べる。
3. 「変更内容をプレビュー」で、すべてのタスクの現在期限・提案期限・状態を確認する。
4. 全タスクについて、今回の扱いを明示的に選択する。
   - **現在の期限を保持**：期限・タスクの版を更新しない。
   - **提案期限を採用**：生成時に保存した相対日数で計算した期限へ変更する。
   - **期限を個別指定**：指定日へ変更する。空欄を明示した場合は期限未設定にする。
5. 最終確認を経て、開催日と選択した期限をまとめて保存する。

初期状態ではどのタスクも選択しない。全件の扱いを選ぶまで確定できない。
「すべての期限を保持」または「算出できる提案期限をすべて採用」を使った後、各行を調整できる。
一括採用には完了済み・個別変更済みのタスクも含むことを画面と最終確認で示す。

完了済みを自動除外したり、個別変更した期限を自動上書きしたりする恒久ルールは設けない。
運営側が今回の変更について明示的に選んだ処理だけを実行する。
これは仕様書U11の例外ルールを確定したことを意味しない。

## 計算と表示

- テンプレートから生成したタスクは、**生成時点**で保存した相対日数を使う。
  後からテンプレートを編集・無効化しても、既存タスクの計算条件は置き換えない。
- 提案期限の採用後は、そのタスクの計算基準日も新しい基準日に更新する。
- 現期限が保存済み基準日＋相対日数と異なる場合は「生成後に期限変更あり」を表示する。
  差分のない固定日指定など、利用者の意図を推測して分類しない。
- 手動登録のタスクは相対日数がないので、期限の保持か個別指定を選ぶ。
- 複数開催日から基準日を勝手に選ばない。基準日がない場合も保持・個別指定で日程を変更できる。
- 日程未定への変更も可能。開催日の削除をイベント中止・タスク削除・外部予定取消と解釈しない。
- 期限は暦日で計算する。休日の繰り上げなどの追加業務ルールは適用しない。
- 日程変更によってタスク状態、重要設定、主担当、協力者を変更しない。

## 通常の編集画面との関係

通常のイベント編集では日程を表示し、変更画面へのリンクを置く。
従来の `PATCH /api/seminars/{id}` で日程だけを変更しようとした場合は409を返し、確認経路へ案内する。
日程の変更がない通常の基本情報編集は従来どおり利用できる。
APIクライアントで日程を変更していた場合は、以下のプレビュー・確定APIへ移行する。

## API

| メソッド | URL | 内容 |
| --- | --- | --- |
| POST | `/api/seminars/{id}/schedule-preview` | 変更後の `dates` と任意の `base_date` から変更候補を取得 |
| POST | `/api/seminars/{id}/reschedule` | 同じ日程・基準日、`preview_token`、全タスクの `decisions` で確定 |
| GET | `/api/seminars/{id}/schedule-history` | 最新50件の日程変更履歴 |

すべて認証必須。書き込みには同一Originが必要。
`dates` はYYYY-MM-DDの配列（重複不可、最大100件）。空配列は日程未定。
`base_date` を省略して開催日が1つならその日を使う。nullは基準日なしを明示する。
複数日程の場合は省略時に特定の日を選ばない。

選択値はタスクごとに以下のいずれか。すべてのタスクを1回ずつ指定する。

```json
{"task_id": 1, "action": "keep"}
{"task_id": 2, "action": "proposed"}
{"task_id": 3, "action": "custom", "due_date": "2027-02-05"}
```

`custom` の `due_date` はnullで明示的な期限解除を表す。
提案期限がないタスクには `proposed` を指定できない。
タスクの追加・削除・内容変更、イベント日程・種別の変更など、プレビュー対象が変わった場合は409。
プレビューを再取得して選択し直す。

## 保存と監査

- 開催日、期限、計算基準、タスク監査、日程変更履歴を同一DBトランザクションで保存する。
  途中で失敗した場合、イベントだけ、あるいは一部の期限だけを更新しない。
- 同じ確認内容の再送は前回の結果を返し、日程履歴・タスク履歴を二重作成しない。
  同じ確認トークンで選択だけを変えた再送は409で拒否する。
- 日程変更の保存では、並行して変更された会場などの対象外フィールドを保持する。
- `event_schedule_state` は確認後の更新競合を検出するための世代番号。
- `event_schedule_history` に旧／新開催日、操作アカウントID、選択内容、更新タスクID、時刻を保持する。
  名称・説明・参加者情報などの自由記述を履歴へ複製しない。
- 各タスクの期限の前後は既存のタスク変更履歴にも記録する。
- イベント削除後も監査記録はDBに保持する。削除済みイベントの監査閲覧画面は未実装。
- 通知・カレンダー更新・メール送信などの外部処理は行わない。

`npm test` で個別判断、完了済み・手動タスク、複数日程、再計算条件、競合、再試行、監査失敗時のロールバックを検証する。
`npm run build` 後の `npm run test:smoke` では、一時DBと架空ユーザーだけで認証付きAPIの操作と通常編集の保護も検証する。
`npm run lint` の既存メール画面の警告1件は継続。
